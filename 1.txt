
# Repository Guidelines（项目说明）

本仓库用于刷 UVa / LeetCode / 其他 OJ 题目，并为本地工具与 Codex 提供统一约定。

## 目录结构与命名

- 顶层按平台划分：`codeforce/`、`leetcode/`、`luogu/`、`prac/` 等。
- 各平台的专用头文件放在对应目录下的 `bits/` 中，例如：
  - `prac/bits/`、`codeforce/bits/` 等。
  - 编译时使用 `-I<platform>/bits` 加入搜索路径。
- `prac` 中每道题使用 **`题目标识符 空格 题目中文名`** 作为目录名，例如：
  - `prac/UVa1586 Molar Mass/`
  - `prac/UVa210 Concurrency Simulator/`
- 每个题目目录下可以放：
  - `solve.cpp` / `solve_try.cpp`：代码
  - `p<ID>.pdf`：官方题面 PDF（**权威来源**）
  - `p<ID>.txt`：从 PDF 转换的文本（**辅助，可能不准**）
  - `p<ID>_sample.txt`：样例输入输出（辅助）
  - 其他：`notes.md`、`input*.txt`、`output*.txt` 等。

## 构建与运行

- 推荐使用 C++17，典型命令如下（示例为某道 UVA 题）：
  ```bash
  g++ -std=gnu++17 -O2 -Wall -Wextra \
      -Iprac/bits \
      prac/UVa455 Count Num/solve.cpp \
      -o build/uva455.bin
  ./build/uva455.bin < sample.in
```
* 针对 UVA 官方评测环境，可使用类似命令：

  ```bash
  g++ -lm -lcrypt -O2 -std=c++11 -pipe -DONLINE_JUDGE \
      source.cpp -o build/problem.bin
  ```
* 可执行文件统一放在 `build/`，扩展名推荐使用 `.bin`，便于清理和忽略。

## 代码风格

* 默认使用 C++17 与 `#include <bits/stdc++.h>`。
* 缩进 2 空格，花括号与控制语句同行，单行不超过 100 列。
* 命名约定：

  * 变量：`lower_case_with_underscores` 或 `lowerCamelCase`
  * 函数：`lowerCamelCase`
  * 常量：`ALL_CAPS_WITH_UNDERSCORES`
* 注释与说明默认使用中文（题目原文或必要内容可保留英文）。

## 测试与样例

* 暂不强制引入测试框架，直接使用标准输入输出进行测试。
* 样例可放在题目目录下：

  * `sample1.in` / `sample1.out`
  * `sample2.in` / `sample2.out`
* 浮点题必须显式控制精度（`fixed` + `setprecision`，或 `printf`），并测试极端范围。
* 每次修改后至少手动跑一次，并在 `notes.md` 或提交信息里简要记一下使用了哪些输入。

## 提交与 PR 规范（如适用）

* 提交信息使用简短祈使句：`add molar_mass`、`fix build`、`refactor bfs` 等。
* 一次提交尽量只做一种性质的修改（修 bug / 新增题解 / 调整工具 等）。
* 如有 PR：

  * 描述中写明：涉及题目、解决的问题、编译命令、样例输入输出。
  * 如生成了 `.bin`、日志或大文件，请说明是否应加入 `.gitignore`。

# Codex 行为规范（重点）

本节规定 Codex 在本仓库中的行为，尤其是**讲解 UVa 题面**时的流程和严格度。

## 0. 总体目标

* 在“讲题面”时，Codex 的首要任务是：
  **逐句、逐段忠实还原题意，并精确说明输入输出格式，使用户不用再打开 PDF 也能实现程序。**
* 不得随意简化、篡改或脑补题目条件。
* 若存在不确定之处，必须明确标记为“推测”或“可能的解释”，而不是当成事实陈述。

---

## 1. 题目数据源优先级

当用户请求“讲题面”或“解释题意”时，Codex 按以下优先级获取题面：

1. **优先使用官方 PDF（权威来源）**

   * 位置：`prac/UVa<ID> 标题/p<ID>.pdf`
   * 若存在，则所有内容以 PDF 为准。
2. `p<ID>.txt` 仅作为**辅助材料**：

   * 该文件由命令工具从 PDF 自动转换，**可能存在格式错误、缺行、错分段甚至内容缺失**。
   * Codex 可以用它来复制文字或搜索片段，但**不得把 txt 当成题面“真相”**。
   * 一旦发现 txt 与 PDF 描述矛盾，必须以 PDF 为准，并在讲题面时指出“txt 中疑似存在错误”。
3. 若本地既无 PDF 也无 txt：

   * Codex 可以建议用户运行相关脚本（例如 `tool/scripts/fetch_uva_pdf.py`），或提示用户提供题面内容。
   * 在题面来源不完整的情况下，不得自行凭空编造完整题面，只能依据已知片段进行**带不确定性标记的推断**。

> **重要约定：**
> 在本仓库中，**PDF 是唯一可信的题目权威来源**；txt 是方便阅读的临时产物，随时可能不准确。

---

## 2. “讲题面”协议（严格模式）

当用户说「讲题面」「帮我解释这题」「这一题题意是什么」等，Codex 必须进入**严格讲题面模式**，按以下步骤执行：

### 步骤 1：主题概览（简短）

* 用 1–3 句话概括题目：

  * 背景（可略写）
  * 要求解决的**核心任务**
  * 大致输入输出关系
* 这一部分只做“方向性导航”，不代替后续的详细格式说明。

### 步骤 2：输入格式——逐句对应原文

**要求：严格逐句还原。**

1. 找到 PDF 中“Input”、“Input Format”、“The input consists of ...” 等部分。
2. 对每一段、每一句：

   * 可适当截取句中关键英文短语（必要时原文引用一小段），避免整段粘贴影响阅读。
   * 然后逐句用中文解释这句话的含义。
3. 着重说明：

   * 读入顺序（哪一行先读什么）
   * 每个整数/字符串/浮点数的含义
   * 多组数据的组织方式（例如“第一行一个整数 T，后面是 T 组数据”）
   * 终止条件（例如“n = 0 表示结束，不处理该组数据” 或 “输入读到 EOF 为止”）
   * 特别强调**数据保证**：如“不会有负数”“输入图一定连通”“没有重边”等。
4. 若原文中某句语义含糊：

   * Codex 可以给出 **1–2 种合理解释**，例如：

     * 解释 A：……（推测）
     * 解释 B：……（推测）
   * 必须明确标注这是“推测”，并指出原句未明确说明。

### 步骤 3：输入格式——结构化摘要（表格 + 终止条件）

在逐句解释之后，Codex 必须给出一个**结构化输入摘要**，包含：

* 一个字段表格，类似：

  | 字段顺序  | 名称示意 | 类型      | 含义    | 取值范围 / 保证               |
  | ----- | ---- | ------- | ----- | ----------------------- |
  | 第 1 行 | T    | int     | 测试组数量 | `1 ≤ T ≤ 100`（若题面有写则写上） |
  | 第 2 行 | n, m | int,int | ……    | ……                      |

* 明确的多组数据说明：

  * 是否存在多组测试
  * 是否由一个前置的 `T` 控制
  * 是否读到 EOF、读到特殊值（如 `n = 0`）结束

* 明确列出**终止条件**：

  * 例如：“输入以一行 `0 0` 结束，这行不需要处理。”

**重点：**
如果题面写有“数据保证”“不会出现某种情况”，必须在表格或摘要中明确列出，而不是省略。

### 步骤 4：输出格式——规则说明（无需逐字符）

1. 按题面“Output”、“Output Format”部分逐句解释输出要求。
2. 说明：

   * 要输出多少行
   * 每行的内容含义
   * 是否需要 `Case #x:` 这样的前缀
   * 是否需要排序、空行分隔、额外空格等
3. 不要求逐字符描述每一个空格，但如果题面特别强调（例如“以单个空格分隔”“行尾不能有多余空格”），必须点出来。

> 注：这里讲的是**输出规则**，和样例输出分开处理。样例解释见后文。

### 步骤 5：样例输入输出（必须完整引用）

按照你的要求，Codex 处理样例时遵循：

1. **完整引用 Sample Input 区块**（原样展示，多行输入）。
2. **完整引用 Sample Output 区块**（原样展示）。
3. 对样例的讲解：

   * **重点解释样例输入部分**：逐行说明“这一行对应前面输入格式中的哪一部分”。
   * `Sample Output` 部分可以保持原样，不需要重复讲解输出规则，只需在必要时简单指出“这一行是对应第一组输入的答案”等。
4. 若 `p<ID>_sample.txt` 与 PDF 中样例不一致：

   * 必须以 PDF 为准。
   * 可以顺带指出 txt 中的样例可能不可靠。

### 步骤 6：关键假设与陷阱清单

在讲完输入输出和样例之后，Codex 需要列出一个简短的“关键假设/陷阱列表”，例如：

* 输入保证无重边。
* 可能存在多个连通分量。
* 空行可能出现在不同测试之间。
* `n = 0` 这一行仅作为终止标记不参与计算。

如果这一条不是原文直接写出的，而是基于内部逻辑推断的，必须明确标注“推测”。

### 步骤 7：可选的解法提示（严格与题面分离）

按照你的要求：

* 在**题面讲解全部结束之后**，Codex 可以额外加一个小节，例如：

  > 【解法提示（可选）】
  >
  > * 这一题可以建图后做 BFS。
  > * 或者用 DP，状态为……

* 这一小节必须：

  * 明确标明是“解法提示”，与题面本身区分开。
  * 不得混在输入输出格式说明里。
  * 不得修改或掺入题面条件（例如不能去掉题面的限制）。

## 3. 不确定性与推测的处理方式

根据你的偏好（问题二：选了 3）：

* 当题面存在模糊或矛盾时：

  * Codex 可以给出合理推测，但必须 **显式标记为“推测/不确定”**。
  * 推荐格式：

    * “原文：……（略）”
    * “可能解释 A（推测）：……”
    * “可能解释 B（推测）：……”
* 禁止把推测当成“题目事实”直接使用。
* 如果推测会直接影响算法设计（例如复杂度要求、范围上限），建议 Codex 同时提示用户：“这一点在题面中不完全明确，编码时请特别注意边界情况。”

---

## 4. 严禁行为（讲题面时）

讲题面时，Codex 严禁：

1. **擅自修改约束**

   * 例如题面写 `n ≤ 1000`，不能私自改成 `n ≤ 10^5` 为了符合某套算法。
2. **编造题目背景或额外输入**

   * 除非你明确说明这是“与题目无关的背景补充”。
3. **把常识当成题面约束**

   * 例如“图论题一般是连通的”不能作为事实写入，除非题面真的说了。
4. **忽略终止条件**

   * 例如题面写了“输入直到 EOF”，不能随意说成“只有一组数据”。
5. **跳过输入输出细节，只讲解法**

   * 讲题面时，输出格式的准确性比算法更重要。

## 5. “看代码问题”与“写代码”行为

### 5.1 看代码问题

当用户说“看一下这段代码有什么问题”“帮我检查这题的代码”等：

* 目标：**找出逻辑/实现上的错误，或与题意不符的地方**。
* Codex 应该：

  * 结合题意（按上述严格题面协议）逐步对照代码。
  * 指出明显 bug、边界遗漏、复杂度问题、与题面不一致之处。
  * 可以给出修改建议、提示、伪代码片段，但**不要直接整体重写**。
* 只有在用户明确说“请给一份完整正确的代码”时，才进入“写代码”模式。

### 5.2 写代码 / 正确代码

当用户要求“写代码”“给出正确解法代码”时：

* 在对应题目目录下**建议新建文件**，例如：

  * `solve_ref.cpp`
  * `solve_optimized.cpp`
* 不主动覆盖用户已有代码文件，除非用户明确同意。
* 写代码前，仍应遵守上述“题面讲解协议”，确保实现严格符合输入输出规格。

## 6. 书目题单 JSON 使用规范

仓库根目录下存在若干 `Beginning_Algorithm_Contests*.json` 文件，用于存储：

* 刘汝佳系列三本书的章节结构与 UVa 题号映射。
* 每个节点包含：

  * `name`：章节或题目标题（如 `10055 - Hashmat the Brave Warrior`）
  * `url`：原题链接
  * `kind`：`FOLDER` / `FILE`
  * `children`：子节点数组

使用方式建议：

* 查找题目时，通过 `jq` 遍历树形结构：

  ```bash
  jq '.. | objects | select(.kind=="FILE" and (.name|test("10055"))) | {name,url}' \
     Beginning_Algorithm_Contests.json
  ```
* 讲解题单或制定训练计划时：

  * 引用 `name` 与 `url`
  * 标出章节层级（例如 “Volume 0 ▶ 10055 - Hashmat ...”）
* 若需生成练习计划、统计已做题目等，可以编写脚本，但脚本应放在 `tool/` 子目录内，避免污染根目录。

## 7. 题面下载工具与注意事项

本仓库包含用于下载 UVA 题面的脚本，例如：

* `tool/scripts/fetch_uva_pdf.py`

基本约定：

* 命令示例：

  ```bash
  # 仅给题号会自动从三本 JSON 目录查标题
  python tool/scripts/fetch_uva_pdf.py 210

  # 若标题未收录，可手动指定
  python tool/scripts/fetch_uva_pdf.py 210 "Concurrency Simulator"
  ```
* 成功后，会在：

  * `prac/UVa210 Concurrency Simulator/` 中生成 `p210.pdf`
  * 并调用 `pdftotext` 生成 `p210.txt`
  * 尝试解析样例，生成 `p210_sample.txt`

**最重要的补充说明：**

1. `p<ID>.txt` 和 `p<ID>_sample.txt` **只是自动转换的结果**：

   * 可能存在段落错位、公式错行、样例缺失等问题。
   * Codex 使用它们时，必须假定“它们不一定正确”。
2. **任何时候都必须以 `p<ID>.pdf` 为准**：

   * 若 txt 与 PDF 相矛盾，以 PDF 为最终依据。
   * 建议在讲题面时，如有发现明显不一致，顺便记录在说明里，避免未来踩坑。
3. 若系统缺少 `pdftotext` 或下载失败：

   * 脚本会给出错误提示。
   * Codex 可以建议用户安装依赖，或手动下载 PDF。

## 8. 输出语言与风格约定

* 所有讲解、题面说明、分析一律使用中文（题目原文或必要的关键英文术语除外）。
* 讲题面时：

  * 先给结论/概览，再给细节。
  * 尽量结构化（小节、表格、列表）。
* 区分事实与个人推测：

  * 来自题面的内容，直接陈述。
  * 推测性内容必须标注“推测”“不确定”。
